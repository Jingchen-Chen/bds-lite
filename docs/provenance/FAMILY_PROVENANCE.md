# Which trained models are "the main matched family"? (finding, 2026-11-02)

## Finding

The submitted manuscript's Table 2 / Table 3 / Fig. 2 numbers for U-Net and BDS-Lite were
computed from `outputs/runs/{dataset}_{unet,bds_lite_full}_seed{1,2,3}/best.pt`
("family O"; source chain: results/submission_candidate_manuscript_v1/tables/
table2_matched_main_results.csv -> results/final_manuscript_audit_v2/
recomputed_main_test_means.csv -> outputs/evaluations/*_test.json).

The revision's existing evaluations (official ISIC test, stacked volumes, gate identity,
surface CDFs, error decomposition) and the new WP5 adapter use
`results/checkpoints/{dataset}_p1b_{unet,bdslite_full_current}_seed{1,2,3}`
("family p1b"; ISIC October followup U/F are bit-identical aliases of p1b).

All 18 family-O vs family-p1b model state hashes differ; selected epochs differ (e.g.
ACDC U-Net seed1: O epoch 105, p1b epoch 16). Hyperparameters, splits, seeds, schedule
and loss weights are the same, except that **p1b ACDC BDS-Lite uses foreground class
weights [1.5, 1.0, 1.25]** (soft Dice and SDF terms), which family O ACDC BDS-Lite does
not. Family O was trained by pre-release commit 5914d35 (`train.py --deterministic`),
which is not present in the preserved history; the training code that produced family O
therefore cannot be re-executed. Family p1b is reproduced exactly by the released code
through scripts/revision/train_run.py: ISIC full seed1 re-training reselects epoch 82 with
identical validation DSC, and its 1,000 official-test per-image metrics are bit-identical
to the historical p1b checkpoint (max |dDSC| = 0).

The manuscript's gate-collapse paragraph ("separate multi-seed checkpoint family ...
0.8607->0.8610, 0.7847->0.7851, 0.8466->0.8449") refers to family p1b.

## Decision (agent recommendation; human approval required)

The revision uses **family p1b** as the primary matched family because it is the only
family whose training is re-executable with the released code, and all new ablations
and comparators (queue A/B) are trained with that exact pipeline. Family O is not
discarded: it is reported as the original-submission family (supplementary), and its
U-Net/BDS-Lite checkpoints should be evaluated with the same unified evaluator (official
ISIC test, ACDC/Synapse test) as a cross-family replication check. The response letter
must state this transparently. Family-O April ablation arms (`unet_surface_loss`,
`bds_lite_boundary_only`, `bds_lite_gate_surface`, ...) are a historical grid from
non-recoverable code and are not mixed with p1b-matched arms.

## Consequences for the narrative (data-driven, revision family p1b)

- ISIC: on the official 1,000-image test, the full recipe vs U-Net differences lie inside
  the SESOI bands for all five metrics (DSC -0.004, Boundary F1 +0.004, HD95 and ASSD
  slightly worse); the submitted validation-split HD95/Boundary-F1 benefit is not
  established on independent test data.
- ACDC: p1b full recipe has higher DSC/IoU/Boundary F1 than U-Net on the slice-level
  cluster analysis, but the comparison is confounded by class weighting; the M0w control
  (U-Net + the same class weights) is required before attributing it to BDS-Lite.
- All numbers must come from revision/tables/families/*.csv generated by
  analysis/revision/family_statistics.py.

## Metric convention (F9)

Primary slice/image convention for means and paired tests: per foreground label,
pairs with empty prediction and empty reference are undefined and excluded; a missed
structure (reference non-empty, prediction empty) or false alarm (reference empty,
prediction non-empty) scores DSC/IoU/Boundary F1 = 0 and has undefined HD95/ASSD
(reported separately as missed-structure / false-alarm rates and in diagonal-penalty
sensitivity analyses). The submitted manuscript's Table 2 instead averaged all
(sample, label) rows with both-empty = 1, which inflates Synapse slice DSC
(e.g. p1b U-Net 0.842 vs 0.487 under exclusion); this is one reason slice-level values
are not comparable with volume-level literature numbers.

## Addendum: family O used a different ISIC2018 split

`outputs/runs/isic2018_{unet,bds_lite_full}_seed*/config_resolved.yaml` point to
`splits/isic2018_split.json` (split seed 1: 1,815 train / 389 val / 390 test), not the
locked seed-2026 manifests (2,075 / 519) described in the submitted manuscript. The saved
family-O per-image CSV overlaps the locked development split in only 77 images, while
the corresponding JSON summary (used for submitted Table 2) records n = 519; the CSV/JSON
pair is therefore internally inconsistent and cannot be used to reconstruct the
submitted ISIC numbers. ACDC/Synapse family-O evaluations use the locked test IDs
(366 / 1,568 slices). This is a further reason to anchor the revision on family p1b,
whose training uses exactly the locked manifests. Family O is evaluated on the official
ISIC test set and ACDC/Synapse test sets with the revision evaluator
(analysis/revision/evaluate_extra_cohorts.py; parity on the 77 shared development images:
max |dDSC| <= 7.8e-4, tolerance 2e-3, see revision/extra_cohorts/famO_*_parity.json).
The response letter must disclose that the original ISIC numbers came from a model
family trained on a different split than stated.
